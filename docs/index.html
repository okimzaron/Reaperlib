Reaper / Docs / Introduction

Introduction

Reaper is a VEX V5 code template for PROS. It's built on EZ-Template and adds the things a competition robot needs past the drivetrain: a lift controller, mechanism sequences, distance-sensor localization, a touch-screen dashboard, a controller readout and startup safety checks.

What's included

AreaWhat you get
DrivetrainEverything EZ-Template 4.0 does: PID drive/turn/swing, odometry, boomerang, pure pursuit, a PID tuner and joystick curves. Exit conditions are reworked to catch a robot that's stuck or pushed.
SetupAll ports and sensor positions in one file, robot_hardware.hpp. All driver buttons in another, robot_controls.hpp. Duplicate buttons fail the build.
LiftOne background controller with travel limits, named presets, optional rotation sensor, gravity compensation, gain scheduling and fault detection.
SequencesLift, claw, pneumatic and wait steps that run in order without blocking your code.
Pneumaticsez::Piston plus ez::PistonGroup for pistons that fire together.
LocalizationUp to four distance sensors correct the robot's X/Y position against the field walls.
Brain screenAn animated scythe splash during calibration, then a touch dashboard with Home, Routes (15 match + 3 skills slots, red/blue alliance), Motors and Sensors pages.
ControllerLive X/Y, heading and lift position on the controller screen.
TestingDown + B runs the selected auton when no field is connected. Press it again to cancel.
DiagnosticsMotor monitor, IMU motion monitor (VMP: still / hit / tip / lift-sway detection) and clear startup messages.
Beta

Reaper 1.0 is still in beta. Test every setting on your own robot before you compete with it. Every port ships set to 0 (disabled), so nothing moves until you configure it.

Installation

Reaper is a full PROS project. You download it, open the folder in VS Code and build it like any other project.

Download ZIPView on GitHub
  1. Install the tools

    Install VS Code, then open Extensions, search for PROS and install it. It installs the PROS command line tools and the ARM compiler for you. Restart VS Code once it finishes.

  2. Download Reaper

    Use Download ZIP above (or Code → Download ZIP on GitHub) and unzip it somewhere easy to find, such as Documents/Reaper. Avoid OneDrive or other synced folders: syncing can lock files mid-build.

  3. Open the template folder

    In VS Code, use File → Open Folder and pick the template folder, the one that contains project.pros.

  4. Build

    Open the PROS sidebar and click Build, or run pros make in the PROS terminal. A clean build shows no errors. The first build takes a minute or two.

  5. Set your ports

    See Hardware configuration.

  6. Upload

    Plug the brain or controller in by USB and run pros mu (make and upload). Pick a program slot on the brain if asked.

pros mu

First boot checklist

Run through this with the robot on a stand, wheels off the ground.

  • The scythe splash plays while the IMU calibrates. Don't touch the robot until it finishes.
  • The controller rumbles once (.). Three long rumbles (---) mean the IMU did not calibrate. Check its port and cable.
  • The Motors page (the M button on the brain) shows every motor green and OK. Red means unplugged, wrong device or a port used twice.
  • Push both joysticks forward. Every drive wheel spins forward. If one side spins backward, flip the sign of that side's ports.
  • Turn in place. The heading on the controller screen (H:) goes up when you turn right (clockwise).
  • Only then put the robot on the ground.

If you have a lift, follow the calibration steps in Lift before driving it. Its upward travel stays limited until you set its height.

Hardware configuration

All wiring and sensor positions live in include/robot_hardware.hpp, between the SETTINGS and END SETTINGS markers. Edit that section, rebuild and upload. Don't change ports anywhere else.

Rules for every port

  • 0 means disabled. The device isn't created and nothing tries to talk to it.
  • Smart ports are 1 to 21.
  • A negative motor port reverses that motor. Fix direction here, not by negating power in your code. Doing both cancels out.
  • Never use one port for two devices. The Motors page marks a port used twice as USED.

Drivetrain

static inline const std::vector<int> DRIVE_LEFT_PORTS{-1, -2, -3};   // negative = reversed
static inline const std::vector<int> DRIVE_RIGHT_PORTS{4, 5, 6};
static constexpr double DRIVE_WHEEL_DIAMETER = ez::wheel::NEW_325;  // inches
static constexpr double DRIVE_WHEEL_RPM = 450.0;      // speed at the wheel, after gearing
static constexpr int IMU_1_PORT = 10;

DRIVE_WHEEL_RPM is the RPM at the wheel, after gearing. A 600 RPM cartridge geared 36:48 is 450.

Distance sensors

Each localization::Mount is {port, x, y, heading, scale}, measured from the robot's turning center to the sensor's face. +X is right, +Y is forward, and heading is clockwise from forward (front 0, right 90, back 180, left 270). Leave scale at 1.0 unless a sensor reads consistently long or short.

After you change anything

Rebuild and upload, check that every configured motor is green on the brain's Motors page, and read the terminal (pros terminal) for [Lift], [VMP] or [Reaper] messages about rejected settings.

Driver controls

Every button is set in one file, include/robot_controls.hpp, the same way ports live in robot_hardware.hpp. Change a binding there, rebuild, upload. Nothing else needs editing.

static constexpr Button LIFT_UP = btn::R2;      // change to btn::UP, btn::X, ...
static constexpr Button ROLLER_TO_COLOR = btn::A;
  • Button names: btn::L1 L2 R1 R2 UP DOWN LEFT RIGHT X B Y A, or btn::NONE to leave an action unbound.
  • The build fails if two driver actions share a button, with the message two driver actions are mapped to the same button.
  • Claw powers are set there too.

Known overlap

EZ-Template's joystick curve buttons are on by default (CURVE_BUTTONS_ENABLED in robot_controls.hpp) and use Left/Right for the left stick curve and Y/A for the right. So Left (lift return) and A (roller) also change a curve, and the change is saved to the SD card. Startup prints each overlap to the terminal. Set CURVE_BUTTONS_ENABLED = false or move them to fix it.

Down + B: testing autons

  1. Pick a route

    On the brain's Routes page, with no field controller or competition switch connected.

  2. Hold Down and press B

    The auton runs, and joystick driving pauses.

  3. Press Down + B again to cancel

    The drive stops and the lift holds where it is.

When the auton finishes, the drive brake mode goes back to what it was. If a field controller gets connected while a test is running, the test is cancelled.

Brain screen

Startup splash

When the program starts, a 3-second scythe animation plays: the swing, the strike, glass cracking, and the shards falling away to show the dashboard. It covers the IMU calibration happening at the same time, and never cuts it short.

  • To change the length, call reaper_splash::min_duration_set(ms) before reaper_splash::start() in initialize(). The minimum is 1620 ms.
  • To turn the splash off, remove reaper_splash::start(); from initialize().
  • Keep the robot still until it's done. One rumble means the IMU is good, three long rumbles mean it failed.

Making the dashboard yours

The splash stays the same for every team. Everything after it takes its team name, logo and colors from one folder, src/team/. It ships filled in for 4588G Gambit as an example.

inline constexpr const char* TEAM_NAME = "1234A ROBOTS";   // shown when there's no logo

Colors are hex codes written 0xRRGGBB (#1E90FF becomes 0x1E90FF): PAGE, CARD, CARD_PRESSED, TEXT, TEXT_PRESSED, NAV_BUTTON, BORDER, the STATUS_* colors and the alliance button colors. Keep TEXT and PAGE far apart so it reads in a bright venue, and leave the status colors green / red / amber.

  1. Make the image

    A PNG up to about 400 × 200 pixels; 200 × 200 fits best.

  2. Convert it

    In the LVGL image converter choose LVGL v9, color format RGB565 (or ARGB8888 to keep transparency), and a name with no spaces like my_team_logo.

  3. Add it

    Put the .c file in src/team/ and replace its LVGL #include lines with #include "liblvgl/lvgl.h".

  4. Point the theme at it

    In src/team/team_theme.hpp, change gambit_logo to your image's name in both places. Set LOGO = nullptr; to show TEAM_NAME instead.

extern "C" {
LV_IMAGE_DECLARE(my_team_logo);
}
inline const lv_image_dsc_t* const LOGO = &my_team_logo;

Once your logo works, delete src/team/gambit_logo.cpp to make every upload a little smaller.

Anatomy of a route

ez::Auton match_02() {
  return {"Left Side", "Grab the near goal, score, touch the bar.", [] {
    chassis.pid_drive_set(24_in, 110);
    chassis.pid_wait();
  }};
}
  • Name: the title shown on the brain's Routes page. Keep it short.
  • Description: one line explaining what the route does.
  • Body: the code that runs. If you rename the function, update include/autons.hpp and register_routes() to match.

Registering routes

void register_routes() {
  ez::as::auton_selector.autons_add({ match_01(), match_02(), /* ... */ match_15() });
  ez::as::auton_selector.skills_add({skills_01(), skills_02(), skills_03()});
}

Up to 15 match routes and 3 skills routes, in the order they appear on the brain. The selected route is saved to the SD card (auto.txt) if one is inserted, so it survives a power cycle.

What runs before your route

Every time autonomous() starts (on a field or with Down + B), Reaper resets PID targets, the IMU and the drive sensors, sets the position to (0, 0) facing 0°, sets the drive brake to HOLD, enables the lift and stops the roller. To start somewhere else, put this at the top of the route:

chassis.odom_xyt_set(-48_in, -60_in, 90_deg);

Motions

These are EZ-Template functions. Its docs cover every one of them in detail.

chassis.pid_drive_set(24_in, 110);           // drive straight 24 in at speed 110
chassis.pid_wait();                          // wait until it's done

chassis.pid_turn_set(90_deg, 90);            // turn to face 90° (absolute)
chassis.pid_wait();

chassis.pid_swing_set(ez::LEFT_SWING, 45_deg, 90);  // swing on one side
chassis.pid_wait();

chassis.pid_turn_set({24_in, 24_in}, ez::fwd, 90);  // turn to face a point
chassis.pid_wait();

chassis.pid_drive_set(36_in, 110);
chassis.pid_wait_until(24_in);               // do something partway through
lift::move_to("Score");
chassis.pid_wait();

chassis.pid_odom_set({{24_in, 24_in}, ez::fwd, 110});   // drive to a point
chassis.pid_wait();

Use pid_wait_quick_chain() instead of pid_wait() to flow straight into the next motion without fully stopping.

Swinging to a point

The heading is worked out once, when the swing starts, from the wheel the robot pivots on (LEFT_SWING pivots on the right wheel, RIGHT_SWING on the left), so the robot's center ends up lined up with the point. It needs the drive width (chassis.drive_width_set(...)). Use ez::rev to point the back at it.

chassis.pid_swing_set(ez::RIGHT_SWING, {24_in, 24_in}, ez::fwd, 90);  // swing to face a point
chassis.pid_wait();

Robot speed

pose v = chassis.odom_velocity_get();            // field x/y in in/s, theta in deg/s
pose local = chassis.odom_velocity_local_get();  // y = forward speed, x = sideways
pose ahead = chassis.odom_pose_estimate(150);    // where it'll be in 150 ms at this speed

Speeds are smoothed over about 50 ms, and resetting the position never counts as moving.

Mechanisms in a route

Move the lift and claw through the lift module, never with LiftL.move() or claw.move() directly, so the background controller stays in charge:

lift::move_to("Score");             // a preset you measured (see Lift)
chassis.pid_drive_set(12_in, 80);
chassis.pid_wait();
if (!lift::wait_until_settled(3000)) return;  // stop the route if the lift never arrived

For a timed lift + claw + piston combo, use a sequence.

With every PID constant at 0, autonomous motions won't move the robot. Tune them before you write routes.

How to tune PID

PID decides how hard to drive the motors from how far the robot still has to go. Each constant does one job:

ConstantWhat it doesToo lowToo high
P (proportional)Pushes harder the farther from the targetSlow, stops shortOvershoots and wobbles back and forth
D (derivative)Brakes as the robot closes in fastOvershootsSluggish, or buzzes/jitters at the end
I (integral)Builds up over time to finish the last bitStops a little short every timeOvershoots slowly, then oscillates

Tune one motion type at a time, in this order: drive, heading, turn, swing, then the odometry ones if you use them. Use a charged battery and the real field tiles.

  1. Make a test route

    Add a route in src/routes/match_routes.cpp that does one motion and comes back, register it like the others, select it on the brain, and run it with Down + B (no field controller connected).

  2. Start with P only

    Set I and D to 0 and P to something small: pid_drive_constants_set(5, 0, 0) for driving, pid_turn_constants_set(2, 0, 0) for turning.

  3. Raise P until it overshoots

    Upload, run, watch. Keep raising P (by about 20% each time) until the robot reaches the target quickly and starts to go past it and wobble back. That's a bit too much P, which is what you want before the next step.

  4. Add D until the wobble stops

    Raise D in small steps until the robot comes in and stops without bouncing. For turns, D usually ends up around the same size as P or bigger. Once it's calm, you can often raise P a little more and add a bit more D.

  5. Add I only if it stops short

    If the robot is consistently a little short (say 1-2° on turns), add a small I and set start_i so I only works near the target: pid_turn_constants_set(3, 0.05, 20, 15) only integrates within 15°. Most drive tunes don't need I at all.

  6. Test other sizes

    A tune that's perfect for 24 in can overshoot at 48 in. Check short, medium and long moves (6, 24, 48 in; 15°, 90°, 180°) and settle on values that are good for all of them.

ez::Auton tune_drive() {
  return {"Tune drive", "24 in forward, then back", [] {
    chassis.pid_drive_set(24_in, 110);
    chassis.pid_wait();
    pros::delay(1000);                       // pause so you can see where it stopped
    chassis.pid_drive_set(-24_in, 110);
    chassis.pid_wait();
  }};
}

For a turn test, swap the moves for:

chassis.pid_turn_set(90_deg, 110);
chassis.pid_wait();
pros::delay(1000);
chassis.pid_turn_set(0_deg, 110);
chassis.pid_wait();

Heading and swing

  • Heading keeps the robot straight while it drives. Drive 48 in: if it curves off to one side, raise the heading P; if it snakes left and right, lower P or add a little D.
  • Swing turns on one side of the drive. Tune it exactly like a turn, with a swing test route (pid_swing_set(ez::LEFT_SWING, 90_deg, 110)).

After tuning: exit conditions

Exit conditions decide when a motion counts as done. The defaults are safe but slow. Once the robot stops cleanly, shorten the times in pid_*_exit_condition_set(...) a little at a time so pid_wait() ends sooner. If motions start ending before the robot stops, go back up.

Stuck detection

Reaper reworks EZ-Template's exit conditions to detect a robot that's stuck, for example pushed against a wall or blocked by another robot. A pid_wait() no longer ends just because the robot is moving slowly. It ends when the robot stops making progress for long enough. The shortest window it checks is 350 ms, so shrinking velocity_exit_time won't make it trigger on a slow but moving robot.

Lift

The lift module runs the lift and claw from one background task, every 10 ms. Your code only sends it commands ("go to 400", "hold here", "jog up"), so two pieces of code can't fight over it. Positions are in motor degrees, measured from where the lift was when the program started.

FileWhat to set
include/robot_hardware.hppLIFT_LEFT_PORT, LIFT_RIGHT_PORT, CLAW_PORT, optional LIFT_ROTATION_PORT
include/Reaper-Template/lift_settings.hppTravel limit, presets, PID, gravity compensation
include/Reaper-Template/lift_core.hppAll settings and their defaults. Read it, don't edit it.

Calibrating (do this first)

The lift ships without an upper limit, because the right height depends on your robot. Until you set one, it refuses automatic moves above 0.

  1. Start low

    The lift's position at power-on becomes zero. Always power on with the lift at its lowest point.

  2. Set your ports

    The two motors face each other, so one is normally negative.

  3. Measure the travel

    lift_settings.hpp ships with c.allow_unbounded_jog = true. With the robot on a stand, hold R2 to raise the lift to its safe top and read the controller's L: line. Until max_height is set, R2/L2 move slowly.

  4. Set the limit

    Put your measured number in max_height and turn calibration mode off (below).

  5. Check the direction

    R2 must raise the lift and make L: count up. If not, flip the signs of both lift ports.

c.max_height = 1150;           // your measured number
c.allow_unbounded_jog = false; // turn calibration mode off
Leave calibration mode off

With allow_unbounded_jog = true, nothing stops the lift at the top.

Presets

inline std::vector<Preset> presets() {
  return {{"Start", 0}, {"Low", 320}, {"Score", 780}};   // measured values only
}

lift::move_to("Score");                // go to a preset
lift::move_to(500.0);                  // or a raw height
lift::wait_until_settled(4500);        // true = arrived; false = timed out or faulted
lift::next();  lift::previous();       // step to the next preset above/below
lift::set_preset("Mid", 550);          // add or change a preset after startup

Every preset has to sit between 0 and max_height, or the lift refuses to start (L: preset). move_to returns false if the target is outside the limits. Nothing is silently clamped.

Driver control

  • R2 / L2: full power while held (c.full_power_manual_jog = true), stopping at the limits. Releasing holds the current height. Both together: hold.
  • Left: return to 0. If the lift failed its startup check, pressing Left (with R2/L2 released) retries it and re-zeros. Put the lift at the bottom first.
  • Claw: always send power through lift::claw_driver_update(). If it isn't called for 100 ms, the claw stops on its own.

Tuning the lift PID

Do this after calibrating (max_height set, calibration mode off). All of it goes in config() in lift_settings.hpp. The lift's P works in motor power per degree of error: with kp = 0.30, being 100° away asks for 30 power.

  1. Gravity first

    Gravity is a constant pull, and a PID that has to fight it ends up too aggressive everywhere else. Set c.gravity = GravityModel::Constant; and raise c.kg until the lift, raised to the middle, holds itself there without drifting down or creeping up. For a single swinging arm use Cosine and test with the arm level.

  2. Make a test route

    Move between two heights and run it with Down + B. Watch the controller's L: line.

  3. Raise kp

    Start low (c.kp = 0.15;, c.kd = 0;, c.ki = 0;) and raise it until the lift gets to each height quickly and goes slightly past.

  4. Add kd

    Raise c.kd (start around 0.01) until the overshoot is gone. The lift's D brakes on its speed, so it never kicks when you pick a new target. Too much D makes it slow to arrive or buzzy.

  5. ki only if it stops short

    With good gravity compensation the lift rarely needs I. If it consistently stops a few degrees low, add a small c.ki (like 0.001) and set c.integral_zone = 50; so it only builds up within 50° of the target. c.integral_limit caps how big it can get.

  6. Different at the top?

    Many lifts (a DR4B especially) carry more load high up. If one tune can't do both ends, tune it at the bottom and at the top and put both in a gain schedule.

lift::move_to(300.0);
lift::wait_until_settled(3000);
pros::delay(1000);
lift::move_to(800.0);                    // two heights inside your max_height
lift::wait_until_settled(3000);

When it's tuned, tolerance and settle_ms decide when a move counts as arrived, and slew_per_second smooths sudden power changes if the lift jerks when starting.

Gravity compensation

c.gravity = GravityModel::Constant;   // or Cosine for an arm that swings through an angle
c.kg = 12;                            // motor power units (-127..127), measured

Constant adds kg all the time (DR4B, cascade). Cosine uses kg × cos(angle) for a single arm; set c.horizontal and c.degrees_per_motor_degree. It's capped at 80% of max power by default.

Gain scheduling

c.gains = {{0, 0.30, 0, 0.02}, {900, 0.45, 0, 0.03}};   // {position, kp, ki, kd}

Gains blend smoothly between the points and hold the end values outside them. Positions must be in increasing order.

Optional rotation sensor

Set LIFT_ROTATION_PORT to an unused port and LIFT_MOTOR_DEGREES_PER_SENSOR_DEGREE to match your gearing. Keep all heights in motor degrees. If the sensor stops answering, the lift faults instead of guessing.

Faults

The lift stops itself (L: FAULT, motors braked) when a lift motor or sensor stops answering, the two motors disagree by more than encoder_disagreement for 150 ms (a slipped gear, say), or the settings are invalid. Fix the cause, then disable and re-enable the robot.

Claw & pistons

Claw

The claw belongs to the lift task. In driver control send power with lift::claw_driver_update(power) every loop (0 when no button is held). In autons use a sequence. Don't call claw.move() yourself.

Pistons

ez::Piston clamp('A');                 // brain 3-wire port A
ez::Piston wing('B', 5);               // port B on a 3-wire expander in smart port 5
ez::Piston hang('C', true);            // starts with the pin high

clamp.set(true);                       // extend (relative to its start state)
clamp.get();                           // last commanded state

To drive one from the controller, give it a button in robot_controls.hpp and add it to DRIVER_ACTIONS (and DRIVER_ACTION_NAMES in robot_controls.cpp) so the duplicate check covers it:

// robot_controls.hpp
static constexpr Button CLAMP_TOGGLE = btn::Y;

// src/main.cpp, inside the opcontrol loop
clamp.button_toggle(C::held(C::CLAMP_TOGGLE));   // press to toggle

Piston groups

#include "Reaper-Template/piston_group.hpp"

ez::Piston clamp_left('A');
ez::Piston clamp_right('B');
ez::PistonGroup clamp{{&clamp_left, &clamp_right}, 250};   // 250 ms to travel

clamp.set(true);
clamp.status().settled;   // true once 250 ms have passed since the command

"Settled" is only a timer, since the cylinder has no sensor. Time your real stroke and use that number. Declare pistons as globals so they live for the whole program.

Sequences

A sequence runs lift, claw, piston and wait steps in order, in the background. While it runs it owns the lift and claw.

using lift::StepType;
std::vector<lift::SequenceStep> score = {
  //  type,               value, duration_ms, timeout_ms, pistons
    {StepType::Claw,       127,   300,         500},              // grab: 127 power for 300 ms
    {StepType::Lift,       780,   0,           4500},             // raise to 780 (measured)
    {StepType::Pneumatic,  1,     0,           1000, &clamp},     // fire the group
    {StepType::Wait,       0,     200,         400},              // pause 200 ms
    {StepType::Claw,      -70,    250,         500},              // release
    {StepType::Lift,       0,     0,           4500},             // back down
};

if (!lift::start_sequence(score)) return;   // false = rejected (bad step)
// ... the drive can move while this runs ...
if (!lift::wait_sequence(15000)) return;    // false = cancelled, timed out or faulted
Typevalueduration_msDone when
LiftTarget height (within limits)unusedThe lift settles
ClawPower, -127 to 127Required, less than the timeoutThe time is up
Pneumatic1 = set, 0 = unsetunusedThe group's travel time has passed
WaitunusedRequired, less than the timeoutThe time is up
  • Every step needs a timeout_ms. At most 64 steps. The whole sequence is checked before it starts, and one bad step rejects all of it.
  • Driver input on the lift or claw, lift::hold_current(), lift::stop(), lift::cancel_sequence(), a new move_to() or sequence, or disabling the robot cancels it.
  • When a sequence ends early, the claw stops and the lift holds. Pistons stay in their last state.
  • lift::sequence_status() tells you how it ended: Idle, Running, Succeeded, Cancelled, TimedOut or Fault.

Roller

A color roller with its own motor and optical sensor, run by its own background task. Every roller function is safe to call from anywhere. The sensor recognises red, yellow and blue, and the roller turns until your alliance color is in front of it. It never stops on yellow or the other alliance's color.

  1. Set the ports

    ROLLER_MOTOR_PORT (negative reverses it), ROLLER_OPTICAL_PORT and ROLLER_POWER (seek speed, 1-127) in robot_hardware.hpp.

  2. Pick your alliance

    RED or BLUE on the brain's Routes page, or roller::target_set(roller::Color::Blue).

  3. Check the colors

    The Motors page's second line becomes a live readout, e.g. Optical: YELLOW h52 s0.61 p140 [IDLE]. Hold each color in front of the sensor and check it reads right.

  4. Adjust if needed

    Hue windows are in include/Reaper-Template/roller_settings.hpp. Defaults: red ≤ 20 or ≥ 340, yellow 40-75, blue 180-250, saturation ≥ 0.35, proximity ≥ 80.

Driver control: hold A to roll to the alliance color and keep it there; release to stop.

roller::roll_to_target(1500);   // blocking: turn until alliance color, max 1.5 s. True if reached.

roller::seek(1500);             // non-blocking version...
// ...drive somewhere...
roller::wait();                 // ...then wait for it. True if reached.

roller::maintain();             // keep defending the color until stop()/spin()/seek()
roller::maintain_for(1500);     // same, blocking, for 1.5 s, then stop
roller::spin(-60);              // plain power, no color logic
roller::stop();

Localization

Odometry drifts: wheels slip, and every turn adds a little error. Reaper uses up to four distance sensors that see the field walls to pull the robot's X/Y position back to the truth while it drives. It's a particle filter (Monte Carlo localization) of 200 guesses at where the robot is, each scored by how well it explains the readings. Heading still comes from the IMU.

Coordinates

  • The field center is (0, 0). +X is right, +Y is forward as you face the field from your starting side.
  • Headings are clockwise from +Y, in degrees.
  • These match EZ-Template's odometry, so chassis.odom_xyt_set() and chassis.pid_odom_set() line up with the corrections.

Setup

//                                         port, x,    y,    heading, scale
static constexpr localization::Mount DISTANCE_FRONT{ 7,  0.0,  6.5,    0.0, 1.0};
static constexpr localization::Mount DISTANCE_RIGHT{ 8,  5.5,  0.0,   90.0, 1.0};
static constexpr localization::Mount DISTANCE_BACK { 0,  0.0,  0.0,  180.0, 1.0};  // not fitted
static constexpr localization::Mount DISTANCE_LEFT { 9, -5.5,  0.0,  270.0, 1.0};

Measure carefully: an inch of mounting error becomes an inch of position error. With all four ports at 0, localization doesn't run.

How it behaves

  • It runs every 10 ms and corrects the pose about every 30 ms.
  • Readings over 60 in, or with the sensor more than 30° off square to the wall, are ignored. A sensor reading the exact same value twice in a row is skipped.
  • Readings are lined up with where the robot was DISTANCE_SENSOR_DELAY_MS ago.
  • Setting the pose (or the reset at the start of autonomous()) re-centers the filter.
  • Readings below DISTANCE_MIN_CONFIDENCE (60 by default) are ignored. Lower it a little if good walls get ignored a lot; 0 turns it off.

Wall resets

When the robot is stopped against or facing a wall, you can snap one axis to it:

vmp::settle(600);                                           // motion done AND robot really still (or 600 ms)
if (!localization::distance_reset(localization::Sensor::left, 150)) {   // average for 150 ms
  printf("reset refused: %s\n",
         localization::reset_result_name(localization::last_reset_result()));
}

The second number is how long to average for; the median of the readings is used. Leave it out for a single instant reading. A reset is refused if it would move the robot more than DISTANCE_RESET_MAX_JUMP (12 in by default).

NoReadingSensor unplugged, out of range, or not confidentCheck the port; aim squarely at a plain wall

Why settle, and not just pid_wait?

They answer two different questions. chassis.pid_wait() asks the motion controller: "did I reach my target?" It watches the encoders and heading, and returns once the error is small enough. But the robot can still be rocking on its wheels, the lift can still be swinging, and the frame can still be bouncing from the stop. A distance sensor reading taken then is off by a little.

vmp::wait_quiet() asks the IMU: "has the robot physically stopped moving?" It can't tell whether the motion is finished, so on its own it could return in the middle of a smooth, slow drive.

vmp::settle(ms) does both in order: it waits for the motion to finish, then waits up to ms for the robot to be still. Use it anywhere you used to write the two lines. It returns true if the robot really is still, and false if it timed out. Without IMU 1 or IMU 2 it waits a fixed 80 ms instead and returns false. You only need settle before things that need a dead-still robot (wall resets, reading your start position); between ordinary moves, pid_wait() is enough and faster.

Field map

Goals, loaders and barriers sit in front of the walls. List them in include/field_map.hpp and localization ignores any sensor whose beam would pass near one, both in the background filter and in wall resets (which then return Blocked).

map.margin = 2.0;                 // clearance around every obstacle, inches

map.circles = {                   // round things: {x, y, radius}
    {0.0, 0.0, 5.0},
    {21.0, 47.5, 4.0},
};
map.segments = {                  // straight things: {x1, y1, x2, y2}
    {-24.0, 0.0, 24.0, 0.0},
};

It ships empty because the elements depend on the game. Use the same coordinates as your routes, take positions from the game manual's field drawings, and check them on a real field. Include every element taller than your sensors are mounted; the beam passes over anything lower.

VMP

VMP watches up to three IMUs 100 times a second. It only watches: it never calibrates or resets an IMU and never moves a motor.

QuestionWhere you see itFrom code
Is the robot still?Sensors page quietvmp::is_quiet(), vmp::wait_quiet(ms), vmp::settle(ms)
Did it just get hit?Sensors page hits / peakvmp::impact_since(t), vmp::last_impact()
Is it tipping?Sensors page tilt, controller !TIPPINGvmp::warning()
Is the lift swaying?Lift card, controller !LIFT SWAYvmp::warning()

Tuning is in include/Reaper-Template/vmp_settings.hpp. Start the program with the robot flat on the field: the first time it sits still becomes "flat" for the tilt reading.

Tuning with the Sensors page

  1. Still

    Park the robot. Cards should go quiet within a second. If not, raise QUIET_ACCEL_G / QUIET_GYRO_DPS a little.

  2. Hits

    Watch peak while driving normally, then while bumping a wall gently. Set IMPACT_G between the two.

  3. Tipping

    Lean the robot by hand and watch tilt. TIP_WARN_DEG starts the warning, TIP_CLEAR_DEG stops it.

  4. Lift sway

    Raise the lift, stop hard, and watch the lift card's rot. Set SWAY_GYRO_DPS just under the bad-sway number.

In autons

const auto t = pros::millis();
chassis.pid_drive_set(24_in, 110);
chassis.pid_wait();
if (vmp::impact_since(t)) {
  // something hit us during that move: re-check position, back off, etc.
}

Driver warnings: when tipping or sway starts, the controller rumbles once, shows !TIPPING 18deg or !LIFT SWAY, and the drive is capped at TIP_DRIVE_SPEED_LIMIT / SWAY_DRIVE_SPEED_LIMIT until it clears (127 for no cap). For 300 ms after a hit, localization keeps running but doesn't apply corrections.

Motor monitor

A background task checks every configured motor's connection and temperature and feeds the brain's Motors page.

for (const auto& m : motor_monitor::snapshot())
  printf("%s port %d %.0f C\n", m.name.c_str(), m.port, m.temperature);

Two IMUs: EZ-Template compares them. If they disagree by more than 15° (chassis.imu_drift_threshold_set()), it flags the drift.
